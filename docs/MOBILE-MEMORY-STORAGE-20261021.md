## Reproducible issues and narrow fixes

- Every `persistDraft()` eagerly cloned the entire high-resolution batch before its serialized write could begin. Twenty captures while storage/cloud preflight was blocked retained twenty increasing snapshots. Coalesce adjacent not-yet-started draft requests into one full snapshot clone at execution, using request-time metadata copies that share immutable photo strings so cloud reloads cannot replace the requested photos. An intervening queued mutation is an ordering barrier, and an active write still gets a later queued update. The new operation pins owner and database before preflight, snapshot, transaction and completion. No classification or automatic-save decisions change.
- Draft storage failures were swallowed into a generic message that could be replaced by later import status. Add persistent Photo results status and an explicit Retry saving photos button. Quota/abort failure returns false, keeps all in-memory photos, preserves prior durable data and does not announce a successful wardrobe save. Successful retry means unfinished photos persisted locally, not that they became confirmed closet garments. Never delete photographs to make space. The existing cloud bridge defers remote restoration while this same owner has pending/failed draft writes, preventing a remote refresh from replacing the only in-memory originals; successful durable retry releases the hold. The cloud client, backend and account predicates are unchanged.
- `photoToJPEG()` revoked its URL but left its decoded image source and canvas backing store attached until garbage collection. Clear the image source and zero the temporary canvas in `finally` on success, decoder failure and encoder failure. Returned JPEG strings and the 3072px / .94,.88,.82 budget policy remain unchanged. Yield between expensive failed JPEG retries and between files so mobile input/paint can run.
- Skip repeated accepted File object identities inside the same batch without redecoding them. Identical names, sizes and timestamps on distinct File objects do not establish duplicates. Failed decodes remain retryable. Existing content-based duplicate and original-photo/account checks remain authoritative.
- Video already releases its media source, object URL and controls in #133. This work keeps that block exact and reruns its cleanup/account tests rather than duplicating or modifying it.

This is instrumented JavaScript clone-input traffic, **not measured resident memory**, browser internal copies, or a physical-phone percentage.

Browser CI compares the exact baseline converter and draft helper against this head in Android Chromium and iPhone WebKit. It checks original-equivalent encoded photos, three 4032×3024 synthetic inputs producing 3072×2304 source frames, buffer/source cleanup and timer progress. The 500-record wardrobe uses tiny placeholder images; the twenty pending records use full source JPEGs. This is a queue/resource test, not a representative 500-photo phone memory certification.

At 3072×2304, one retained canvas accounts for 7,077,888 intrinsic pixels (28,311,552 theoretical RGBA backing bytes). Zero dimensions after conversion remove that explicit backing-store requirement.
