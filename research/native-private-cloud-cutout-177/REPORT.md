The real native `public/cloud-backup-engine.js` maps only properties named `image`. An actual approved multi-garment cutout is `segmentHint.cutoutImage`. Existing default auto-cloud writer can therefore upload original garment JPEG correctly but leave an independently SHA-reviewed cutout JPEG as inline base64 in the JSON backup and omit its independent private object. This is not a theoretical limitation — P128 previously proved it with a real P119 owner-reviewed IndexedDB source.

New `research/native-private-cloud-cutout-177/cloud-transport.mjs` installs an explicitly opt-in, scoped replacement for **the actual native engine object's `mapImages` callback**. It maps BOTH original `image` fields and separately reviewed `cutoutImage` fields to independent `closet-photo:<ownerUUID>/<SHA256>.jpg` paths. It snapshots the original backup before asynchronous hashing; checks complete P126 original+reviewed-cutout source and owner provenance **before any upload callback**; preflights all remote paths before any private Storage GET (prevents concurrent A source fetch when a B cutout path is in a sibling field); guards owner session lease before and after all async work; rehashes the original and independently reviewed cutout after storage readback **before returning a document suitable for the atomic owner-private restore**. Malformed names, mixed legacy inline/path payloads, prototype pollution, missing review, altered original/cutout JPEG, forged owner, session revocation and unauthorized unknown item approval all fail closed.
